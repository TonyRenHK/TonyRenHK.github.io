CodeBuddy Telegram 通道实战：让无人值守的 AI 编程助手可见、可控、可恢复

2026-10-26
AI

把 CodeBuddy CLI 部署在云服务器上、通过 Telegram 远程指挥它干活，是”随身 AI 编程助手”的经典玩法。但真实跑起来后你会发现：通道正常 ≠ 好用。本文记录一次完整的故障排查与改造过程——从”发消息石沉大海”到”每一步思考实时推送到手机”，期间踩过的坑（伪终端注入误区、硬编码审批弹窗、多层 SSH 引号）都是通用经验，适用于任何类似的 CLI-agent + 消息桥接架构。

一、架构：消息到底是怎么流动的

用 --channels server:telegram 启动 CodeBuddy 后，链路是这样的：

三个容易想当然的点：

  1. 桥接消息不走终端输入，走的是 MCP 通知管道。往 TUI 的 pty 写按键是另一条路，两者互不相通。
  2. 过程不可见是协议设计的：只有模型显式调用 reply 工具，内容才会到 Telegram。中间的思考、工具调用、卡住，用户一概看不见。
  3. Telegram Bot API 的 getUpdates 只允许一个消费者，但 sendMessage 不受限——这给后面”另开一路进度推送”留了口子。

二、事故复盘：三次”没反应”的真相

第 1 次：回车被界面重绘吞了

上一个任务刚结束的瞬间（TUI 正在做收尾重绘），我发出的消息其实已经送达、已经躺进了输入框——但提交它的回车在竞态中丢了。几秒后下一次重绘把输入框草稿清掉，消息彻底消失。

症状特征：日志里能看到停在输入框里的消息文本和 ↵ send 提示，之后零活动。

第 2 次：硬编码的高危审批弹窗（Telegram 永远看不到）

补发消息后，模型开始干活，但一条含 rm -rf 的命令触发了 CodeBuddy 内置的高危操作确认框：

  • 它是硬编码的：正则清单写死在二进制里，bypassPermissions 权限模式也压不住，没有任何配置项能关。
  • 它只在服务器终端的 TUI 里弹出。通道的 Telegram 权限按钮走的是另一套 MCP 通知，覆盖不到这种 TUI 弹窗。
  • 无人值守时，弹窗 = 整条通道死锁。你盯着 Telegram，它盯着终端，谁也等不到谁。

反编译确认后死心：配置层无解。治本思路是让模型的工具调用里根本不出现危险命令文本——见第四节。

第 3 次：按键注入的”安慰剂”

我尝试替用户按键：往进程的 /proc/<pid>/fd/3（一个指向 /dev/ptmx 的符号链接）写字节。写入”成功”了，界面上甚至能看到回显——但会话转录文件纹丝不动，弹窗岿然不动。

折腾了三轮 Esc、数字键、回车之后才意识到根本错误：

/dev/ptmx 每次被 open 都会分配一个全新的伪终端。 我写的所有字节都进了那个无人读取的幽灵终端。所谓”进程 stdin 卡死”是假象，进程活得好好的，只是我的输入从未到达它。

三、两个关键技术

1. 往别人的终端打字：TIOCSTI

正确姿势是打开 pty 的 slave 端（/dev/pts/N），用 ioctl(TIOCSTI) 逐字节塞进终端输入队列（需要 root）：

注入是否生效，不要看终端回显（它会骗你），要看会话转录文件的 mtime 是否前进。

2. 判断真相：转录文件 > TUI

CLI 会把每一次思考（reasoning）和工具调用实时写入会话转录（JSONL）：

  • mtime 在动 = turn 活着；mtime 冻结 = 挂起
  • 最后一条事件的 reasoning 字段直接告诉你模型在想什么
  • TUI 每 60 秒定时重绘一遍界面，看起来”有输出”，但不代表有进展

排查通道问题时，永远先看转录，别信终端画面。

四、治本：rm → 回收站 shim

高危弹窗的死结在于：模型删除文件天然要用 rm，而命令文本含 rm 就触发弹窗。破局方式是改变语义——在 PATH 最前面放一个 shim，让 rm 变成”挪进回收站”：

配套两件事：

  1. 给 agent 写持久记忆（CodeBuddy 的 memory 机制）：”所有删除一律走 shim/mv 到 ~/.trash，绝不使用 /bin/rm；验证删除结果用 ls/cat 读 journal——命令文本里含 rm 也会触发弹窗”。
  2. 误删可恢复（回收站里有时间戳和原路径），真要硬删永远保留 /bin/rm 这条路。

这个模式值得推广：凡是”agent 发出的命令会触发人肉审批”的场景，都可以用语义替换（shim）+ 持久记忆来消除死锁，而不是想办法远程替人按按钮。

五、体感升级：过程流式推送到 Telegram

“没反应”最磨人的地方是不知道它是在干活还是死了。既然每次思考/工具调用都会落进转录文件，那就 tail 它：

要点：

  • 发送直接走 Bot API 的 sendMessage，与通道的 getUpdates 轮询互不冲突（API 只限制后者单消费者）
  • token 从桥接的 MCP 配置里读，白名单取 access.json 的 allowFrom——不引入新凭据
  • 关键细节：attach 时要从文件尾部回读一次、初始化”最后事件时间”，否则服务在事故中途上线时，卡住告警永远不会触发（我们的第一版就栽在这）
  • 每条消息间隔 ≥3 秒，规避 Telegram 频控

上线后的体感：📩 收到消息 → 🤔 思考中 → ⚙️ 正在执行 xx → ✅ 完成 →（最终回复）。终于”看得见它在干活”，卡住也会在 3 分钟内收到 ⏸ 告警。

六、通用避坑清单

  1. 多层 SSH 引号必剥变量：ssh host 'sudo -i bash -c "… $VAR …"' 里 $VAR 会在本地被剥成空串。正确做法是本地写好脚本，ssh host 'sudo -i bash -s' < script.sh 管道进去。
  2. 写 /proc/*/fd/* 里的 ptmx 符号链接 = 开新终端，不是往原终端写。要注入用 TIOCSTI 打 slave 端。
  3. 无人值守 + 人肉审批 = 死局。用 shim 语义替换 + agent 持久记忆消灭危险命令文本，或换成可远程应答的审批通道（如 MCP permission 通知 + inline 按钮）。
  4. turn 收尾瞬间是消息丢失高发期。重要指令避开”刚干完活”的时点，或靠进度推送器的 ⏸ 告警兜底。
  5. 给桥接加 ack 反馈：收到消息立刻回一个 emoji reaction / “typing…” 状态，用户至少知道消息进来了。
  6. 回执、进度、告警三路分离：最终答案走 reply（触发通知），过程流走推送器，卡死告警独立触发——任何一路静默都还有另外两路。

七、结语

这次改造后，远程 AI 编程助手的工作流变成了：Telegram 下指令 → 手机上看实时过程流 → 干完收到正式回复 → 卡住 3 分钟内收到告警 → 误删可从回收站捞回。核心经验一句话：先弄清消息真实流动的管道，再谈可靠性；能用语义替换消灭的审批死锁，就不要建造更精巧的”远程按键”机器。

8.1 组件职责总览

组件 类型 干什么 为什么需要
telegram_progress_watcher.py 常驻进程 tail 会话转录，把思考/工具调用推到 Telegram 通道协议只发最终结果，过程全黑
codebuddy-telegram-progress.service systemd 托管上面的脚本，开机自启、崩溃重启 无人值守必须能自愈
codebuddy-daily-refresh.timer systemd timer 每天凌晨把通道重启进干净会话 + 清理旧转录 会话会漂移/膨胀，且卡死的对话框无法自愈

8.2 telegram_progress_watcher.py（进度推送器）

它解决什么问题：CodeBuddy 的 Telegram 通道在设计上只有模型显式调用 reply 工具，内容才会发到 Telegram。中间的思考、工具调用、卡住，用户一概看不见——发完指令后手机上一片空白，你不知道它是在干活还是已经死了。

思路：CLI 会把每次思考（reasoning）和工具调用实时写入会话转录 JSONL。所以另开一路，tail 这个文件就行。

关键设计点：

  1. 为什么不与通道冲突：Telegram Bot API 只限制 getUpdates 单消费者，但 sendMessage 不限。watcher 只发不收，天然共存。
  2. 不引入新凭据：token 从通道自己的 MCP 配置读，收件人取白名单 allowFrom[0]，不多存一份密钥。
  3. attach 时回读尾部（易忽略的坑）：服务在事故中途上线时，如果不从文件尾部初始化”最后事件时间”，watcher 会以为”刚开始”，180 秒差值永远凑不满 → 卡住告警永不触发。我们第一版就栽在这。
  4. 纯标准库、全程 try/except 兜底，自己永不崩。
  5. 长消息自动分片：send() 不截断——超过 3900 字符按行边界切成多条，带 [i/N] 前缀，内容零丢弃（Telegram 单条上限 4096，超长静默截断是本组件唯一的“丢数据”点，已修）。

上线自检（会真的发一条消息，是端到端最硬的验证）：

8.3 codebuddy-telegram-progress.service（托管 watcher）

它本身不含业务逻辑，职责就三条：开机自启、崩溃重启、依赖顺序。

几个讲究：

  • After=codebuddy-telegram.service：必须等通道起来，否则 watcher 启动时 access.json 可能还没生成，load_chat() 直接退出。
  • Restart=on-failure：watcher 内部虽有 try/except，但环境异常（网络抖动、文件被删）仍可能退出，交给 systemd 拉起。
  • User=<RUN_USER>：与 codebuddy 通道同一个用户，否则读不到 ~/.codebuddy/ 下的转录。

8.4 codebuddy-daily-refresh.timer（每日清洁会话）

干什么：每天定时把通道重启进一个干净会话，顺带清理超过 N 天的旧转录。

为什么需要：

  1. 通道进程长期不重启，会话上下文会持续膨胀；前面踩过”turn 收尾瞬间消息丢失”的坑，干净会话能规避一类竞态。
  2. 卡死的对话框（比如审批弹窗）无法自愈，重启是唯一出路。
  3. 转录文件会不断堆积。

核心是那个守卫：如果当前正有任务在跑，就跳过本次重启——绝不能在人家干活时把它打断。判据是”最新转录文件的 mtime 是否在过去 N 分钟内”（模型每次思考/工具调用都会写转录，所以 mtime 静止 = 没在跑）。

8.5 cb-dialog-answer.service（自动应答审批弹窗）

背景：第四节说过，高危审批弹窗是硬编码的——bypassPermissions 压不住，且只在服务器 TUI 弹出。无人值守时这是死局。

两层解法：

  • 治本（第四节）：shim + 持久记忆，让模型根本不写出危险命令文本。
  • 兜底：这个 watchdog 盯日志，一旦发现弹窗特征，用 TIOCSTI 注入应答。

8.8 这次新增的三条经验

  1. 类型不匹配会伪装成权限错误。 模型常把 chat_id 当数字传给 reply，而白名单里存的是字符串，includes() 严格比较失败 → 报 “chat is not allowlisted”。这是误报，配置其实没错。修法是比对前统一归一化，别去改配置。
  2. 危险命令文本本身就是风险。 shim 让”执行”变安全，但弹窗扫的是命令文本，所以必须让模型根本不写出那个词——这正是”持久记忆”该写的东西。有意思的旁证：我在写这篇文档时，安全策略连续拦截了我好几次，仅仅因为文本里出现了那个词。
  3. 发送端不得静默丢弃内容：旧版把超长消息硬截到 3800 字符——用户看到的是“不完整”而非报错，静默截断比失败更危险。修复后超长自动按行分片、多条发送，实测 11399 字符 → 3 片零丢失。
